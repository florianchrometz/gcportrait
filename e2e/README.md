# @gcportrait/e2e

End-to-end and accessibility (axe) tests with Playwright, and the diagram's visual baselines (`baselines/`).
The tests run against the app in demo mode, plus one spec in normal (live) mode with the backend's answer
stubbed in the browser, so they need no Google Cloud access and no backend. They drive the app through the
browser and never import it. They run under Playwright, not Vitest.

## Running

```sh
pnpm --filter @gcportrait/e2e install-browsers   # once per machine: Playwright's Chromium
pnpm e2e                                          # from the repository root
```

The diagram's visual baselines are not Playwright screenshots (CI runs on Linux; screenshots taken on another
platform never match). They are the renderer's SVG text,
`baselines/diagram/<fixture>-<lens>-<detail>-<theme>.svg`: demo S, M and L at detail `auto` and M at `all`, ×
overview, networking and load-balancing, × light and dark (24 files). The frontend's unit tests write and
compare them (`frontend/src/diagram/baselines.test.tsx`); update them only for an intended visual change, look
at the changed SVGs, and say why in the pull request:

```sh
pnpm --filter @gcportrait/frontend test src/diagram/baselines.test.tsx -u   # the file before -u
```

`baselines/render/` holds the render goldens, `S-overview-auto-light.png` and `S-overview-auto-light.drawio`:
exactly what `pnpm render --fixture S --lens overview` writes, compared tolerance-free by the headless
renderer's tests ([`packages/render-cli`](../packages/render-cli/README.md); its README next to the file says
how to update it). A person reviews a render against the style skill's fact-check list (gcp-diagram-style §11)
and the layout skill's checks (gcp-diagram-layout §8).

`playwright.config.ts` starts two Vite dev servers as its `webServer`s and runs five projects:

| Project | Server | Specs |
|---|---|---|
| `chromium` | demo mode, `pnpm dev:demo`, <http://localhost:5174> | everything except the live specs, `mobile.spec.ts`, `touch.spec.ts` and the tests tagged `@phone` or `@tablet` |
| `chromium-live` | normal mode, the Vite server of `pnpm dev`, <http://localhost:5173> | `live.spec.ts`, `signin.spec.ts`, `preflight.spec.ts`, `live-pull.spec.ts`, `permissions-variables.spec.ts`, `sa-mode.spec.ts`, `demo-only.spec.ts` |
| `mobile` | demo mode, as `chromium` | `mobile.spec.ts` and `touch.spec.ts`: the phone and tablet layouts and the canvas's touch gestures, in Chromium emulating a touch device at the sizes the specs set (`pnpm --filter @gcportrait/frontend mobile` runs this project alone) |
| `chromium-phone` | demo mode, as `chromium` | the tests tagged `@phone` (`handheld.spec.ts`), in Chromium emulating a touch device at 390 × 844, 3× (an iPhone 13's window, the phone's layout) |
| `chromium-tablet` | demo mode, as `chromium` | the tests tagged `@tablet` (`handheld.spec.ts`), in Chromium emulating a touch device at 820 × 1180, 2× (an iPad Air's window, the tablet's layout) |

Locally a server that is already running on either port is reused; on CI (`CI` set) fresh ones are always
started. The live project needs no running backend: its specs answer `GET /api/config` inside the browser
(`fixtures/live.ts`), and the signed-in ones also answer Google's sign-in script and tokeninfo
(`fixtures/gis.ts`), so nothing reaches Google. `sa-mode.spec.ts` and `demo-only.spec.ts` start the backend
itself (`fixtures/harness.ts`), the first with a pretend Google inside it, so nothing reaches Google there
either. Helpers the specs share are in `tests/support.ts`, `tests/timelineSupport.ts`,
`tests/consoleSupport.ts` and `tests/permissionsSupport.ts`. Chromium only for now; the functional specs at a
desktop window of 1440×900, `mobile.spec.ts` at phone and tablet sizes, `touch.spec.ts` at a phone's and
`handheld.spec.ts` at the phone's and the tablet's projects' sizes; light colour scheme unless a test asks for
dark. `pnpm e2e --project chromium-phone --project chromium-tablet` runs the two handheld projects alone. CI
runs the whole suite in four legs (`.github/workflows/pr.yml`): `pnpm e2e --project chromium-live --project
chromium --shard=N/2` and every other project (`chromium-phone`, `chromium-tablet` and `mobile`, a new one
included) with `--shard=N/2`, for N 1 and 2. `--shard` splits the tests by count, in the order of the projects
in `playwright.config.ts`: `chromium-live` comes before `chromium` and the handheld projects before `mobile`,
so that each shard gets a share of the slow tests.
